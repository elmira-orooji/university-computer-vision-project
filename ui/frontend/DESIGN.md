# پیکسل Design System

> Generated by Dig (`npx digdesign design-md`). Tokens above mirror the installed Dig theme and brand.css; regenerate after changing the brand instead of editing values by hand. Prose rules may be extended for this product.

## Overview

پیکسل is a Persian, right-to-left interface built on Dig: calm, current and confident. Surfaces are quiet (white and very light blue-grey), one brand color carries action and emphasis, and marketing pages are bold while in-app pages stay moderate and dense enough to work in.

- The root element is `<html lang="fa" dir="rtl">`. Use logical utilities (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start`), never `left`/`right`.
- Build every control from Dig components (`npx digdesign add <name>`); never hand-roll a native `<select>`, `<input>` or `<button>` when a Dig component exists.
- Style only with semantic Tailwind classes from the tokens below (`bg-primary`, `text-muted-foreground`, `rounded-xl`, `p-card`). Never write a raw hex, rgb or px value in components.
- The brand lives only in `brand.css` (the `--brand-*` ramp). To change it run `npx digdesign theme brand <hex>`, then regenerate this file.
- With the Dig MCP server connected, call `get_page_patterns` before composing a page and `get_block` when a ready block fits; this file holds the same rules for agents without it.

## Typography

One Persian family, IRANSansX, set once through `--font-anchor` in brand.css. Never set `font-family` on body or on individual components.

- Sizes above are fluid (`clamp`) in the theme; use the semantic classes and let them scale.
- Never add letter-spacing (tracking) to Persian text; it breaks joined letters.
- Promo banners are designed, not a flat colored box: one color family as a gradient (e.g. violet to indigo), a soft pattern (dots fading to one side) and an oversized decorative number or shape inside the frame (never cropped), white text, and white chips for timers or badges. Never a full-width saturated red, and no photo collage on mobile. _(marketing, list pages)_
- In-app and article section titles stay moderate (text-xl/2xl, font-bold or semibold); never font-black outside marketing heroes. _(dashboard, list, form, content, support, detail pages)_
- Keep sizes proportional: badges, chips and ratings next to a title match its scale (no tiny badge beside a large title, no huge rating beside a small title).
- Bold is for the page title and the single focal number. Card titles, row titles and table prices use medium or normal weight. _(dashboard, list, detail, form pages)_
- One filled (primary) button per view or card group: in a grid of equal options (rewards, plans except the recommended one, product cards) use outline buttons; the filled button marks the single most likely next step.

## Layout

Containers: `max-w-page` (77.5rem) for pages, `max-w-form` (38.75rem) for forms, `max-w-prose` (65ch) for text. Side gutter `px-gutter` (16px on mobile, 32px on desktop). Layouts work at 375px with no horizontal scroll.

- Choose the composition source after defining the page task and regions. Reuse a block only when its information architecture and interaction model fit; otherwise compose directly from Dig components and the composition plan. Never force a page into the nearest visual-looking block.
- Mobile apps and mobile web apps (PWA) are not responsive websites: use an app shell. Sticky AppBar on top (back or menu, title, at most two actions), BottomNavigation with 3–5 primary destinations on root screens (hidden on detail and form screens), a single column with p-4 gutters, and screen-level flows instead of multi-column grids. Start from the mobile category blocks (mobile-shop, mobile-wallet, mobile-orders, …). _(mobile pages)_
- Every page must fit a 375px screen with no horizontal scroll: page grids start with grid-cols-1 (implicit grid columns grow to their content), text columns beside a chart or image get min-w-0, fixed-width cards (ProductCard vertical) get w-full inside grids, wide segmented controls and tables sit in overflow-x-auto, and decorative shapes live in an overflow-hidden parent.
- Being compact on mobile is a principle: every extra pixel of height is more scrolling. Product and item cards in a two-column phone grid use 40px controls (ProductCardFooter does this; for hand-built cards wrap the grid in ControlSizeProvider size="lg"), gap-2 inside the card, the new and old price on one row, and no element that only repeats text already shown (a stock progress bar under «۱۶ عدد باقی مانده» goes). Banners on mobile keep p-5, a one-line title and compact timer cells. _(list, mobile pages)_
- A table must never need horizontal scrolling on a phone to show status or actions. Use <Table stackOnMobile> (each row becomes a compact card: first cell as title, the rest in two columns of small label above value, the action cell full width) or render a card list below md and the table from md up. Keep horizontal scroll only for true comparison matrices (pricing-compare, product-compare). Never wrap Table in your own overflow-x-auto: Table scrolls itself and its pin prop keeps sticky columns in sync with row hover. _(list, dashboard, mobile pages)_
- Long flows (checkout, booking, passenger info, ticket detail) use a two-column grid: main content start, a sticky summary or properties card end (lg:sticky lg:top-6). On mobile the summary stacks below. _(checkout, detail, form pages)_
- All auth pages (login, signup, forgot password, OTP) share one structure: form column centered (max-w-sm) with brand mark, title and subtitle; a brand panel (product mock + one testimonial) beside it, hidden on narrow screens (hidden lg:flex) so the form and its button stay above the fold. _(auth pages)_
- Pick each chart by the question its data answers, not by habit: compare categories or periods → BarChart (horizontal for rankings), trend over many time points → LineChart, trend where volume or a stacked total matters → AreaChart (expand for mix over time), share of one whole now with ≤5 parts → PieChart donut with the total in centerLabel, progress to a goal → RadialChart with max and showTrack, profile across 5-8 criteria → RadarChart. Start from the closest of the 70 ready cards: get_component_demo({ name: "chart-presets" }) lists them in chart_examples with their use, then get it with example. Give every chart card a one-line takeaway in the footer and units in tooltip.formatValue. _(dashboard pages)_
- In-app pages: page title + one-line description at top, actions on the same row at the end, content in cards below. Toolbars (search, filters) sit outside table frames, 32px above the table; pagination sits outside too. _(dashboard, list, support pages)_
- Article and long text columns are wide enough to read comfortably (about 48–52rem on desktop) with an optional sticky table of contents beside them; headers are start-aligned, not centered. _(content pages)_
- Forms: get_component_demo('form'); use FormLayout → FormHeader → FormFields/FormSections → FormActions. Defaults: title/description 6px, fields 16px, sections 32px, final action 40px (2.5× fields). Measure desktop/390px, errors and wrappers. Inline search buttons stay attached to inputs. On wrapping page headers, separate heading/actions more than title/description.
- Marketing sections use generous vertical rhythm (py-20 to py-24) and a section header of title with its description directly UNDER it (not beside it). _(marketing, content pages)_
- When no full-page block fits a marketing or landing page, compose it from section blocks (list_blocks category sections) in this order: header (navbar | navbar-announcement), hero (hero-split | hero-centered | hero-image), features (features-grid | features-alternating | features-bento), testimonials (testimonials-grid | testimonial-spotlight), cta (cta-banner | cta-newsletter), footer (footer-dark | footer-simple). Pick one variant per section, alternate light and dark/subtle backgrounds between neighbours, and adapt every text and image to the product. _(marketing pages)_
- For landing, dashboard and list pages start from page-level components before hand-assembling cards: PageHero, SectionHeader, FeatureGrid or BentoGrid, StatsBand, TestimonialGrid, PricingGrid, StepList, CtaBand, SiteHeader (page-sections), PageHeader/PageGrid/PageSection (page-composition), AppShell, ChartPanel, StatValue and ListRow. _(marketing, dashboard, list pages)_
- No empty grid cells or half-empty columns: use auto-fit grids (PricingGrid, FeatureGrid, TestimonialGrid) or equal-height columns. Numbers stay inside their card (StatValue); check at 375 and 1440. _(marketing, dashboard, list pages)_
- Direction icons follow reading direction. Forward, next and open-detail chevrons point to the END of the line (left in RTL): use ChevronEndIcon, and place it at the end of the row or card (the left edge in RTL), after the content. Back points to the START: ChevronStartIcon. In a ListRow just pass the chevron prop. Never use ChevronRightIcon for forward in RTL, and never put the detail chevron before the content. _(mobile, list, detail, dashboard, form pages)_
- Lists of rows (accounts, transactions, contacts, settings) are a ListGroup of ListRow items with an IconTile or Avatar leading; one rounded container per list, never bare rows on the page background. IconTile accepts every semantic color (primary, success, warning, destructive, info, violet, indigo, cyan, orange, pink). _(mobile, dashboard, list, detail, form pages)_
- Marketing heroes are bold: very large heading (text-4xl→6xl, font-black), one short subtitle, one primary CTA (size lg) plus one secondary, and a visual (product mock or image) — dark hero when the image is dark, with the image fading into the same background color. _(marketing pages)_

## Elevation & Depth

Depth comes mostly from surface color, not shadow. Cards are flat; shadows are reserved for things that float.

- `shadow-control`: Buttons and inputs: barely there
- `shadow-card`: Cards: none; separate with surface color or a border
- `shadow-panel`: Popovers, dropdowns, sticky bars
- `shadow-overlay`: Dialogs and sheets
- `shadow-float`: Floating product mocks in heroes
- `shadow-hero`: The single hero visual of a marketing page
- AI chat screens feel alive, not like a plain form: a soft ambient gradient behind the conversation (two faint radial glows that also work in dark), a gradient orb as the assistant mark and avatar, a big two-line greeting with the second line in a violet-to-blue gradient, suggestions as a 2-column grid of cards (tinted icon tile, bold title, one-line hint on desktop) instead of outline pills, user messages in a brand gradient bubble, assistant messages in a bordered card bubble, and a floating composer (card background, shadow, gradient send button). On mobile the history lives in a menu sheet. _(chat, mobile pages)_
- The hero visual is a real product window: <DashboardMockup/> (or AppWindow with realistic rows, statuses and amounts) as PageHero media. Never three small cards with gray bars. _(marketing pages)_
- Customer or partner logos are real SVG logos (public/logos or Digche) or <BrandMark name="..."/> for fictional brands, inside LogoCloud. Never plain text names. _(marketing pages)_
- Use the four-level elevation scale and never hand-write box-shadow: level 0 flat and inline; level 1 controls (shadow-control); level 2 surfaces such as Card, card Table and Accordion (shadow-card); level 3 floating panels and overlays (shadow-panel, shadow-overlay). _(marketing, dashboard, list, form, detail pages)_
- Before calling a page done, render it at 1440 and 375 in light and dark, look at the screenshots and fix: headings wrapped into 3+ lines, text logos, cropped or overflowing numbers, empty columns, misaligned badges and titles. _(marketing, dashboard, list, form, detail, auth, mobile pages)_
- An icon missing from Dig's set is never replaced by an icon with a different meaning (GridIcon for QR, StarIcon for a coin, ShopIcon for a bank). Search Digche (recommend_icons or search_icons), fetch the exact SVG with get_icon_svg and add it as a small icon component. _(mobile, dashboard, list, marketing pages)_
- In app screens, secondary actions (transfer, request, deposit) use Button variant="flat" with a color (tinted background, matching icon) and may use radius="full" when the design is pill-shaped. Keep one solid, saturated button for the single primary action. _(mobile, dashboard, detail pages)_
- Emphasis cards (featured plan, testimonial, newsletter, hero) use the bg-inverse surface (bg-inverse-raised for tiles inside, border-inverse-border for lines; never raw graphite-900, which turns into a black hole in dark mode) and invert by redefining base CSS vars on the element (--background, --foreground, --muted-foreground, --primary, --border), never with the dark class.
- Separate areas with surfaces, not extra borders: bg-subtle (lightest blue-grey) for side panels and secondary sections, bg-muted for controls inside them (tabs, hover, selected rows), soft tinted icon tiles (color-mix with brand-secondary or a palette colour at ~12%). Two adjacent surfaces must never share the same grey; the active item uses a brand tint.

## Shapes

Base radius is 10px (`--radius`); the scale is derived from it.

- `rounded.sm` 6px: Small inner elements (rounded-sm)
- `rounded.md` 8px: Buttons, inputs, toggles (rounded-md, the control default)
- `rounded.lg` 10px: Nested containers inside cards (rounded-lg)
- `rounded.xl` 14px: Cards, panels, images, dialogs (rounded-xl)
- Containers, cards, images and panels use rounded-xl (nested: rounded-lg). Buttons and toggles keep their own default radius. Pill buttons are allowed only when the design or brand asks for them: use the Button prop radius="full" (never className rounded-full); never rounded-2xl/3xl.

## Components

Install with `npx digdesign add <name>`; every component already reads the tokens above.

- Every tappable element on mobile is at least 44–48px high (xl controls, size="icon" buttons inside a 48px row), list rows are whole-row tappable with a chevron, and swipe-only actions always have a visible button alternative. _(mobile pages)_
- Run review_code on whole files, never trimmed excerpts: send every file in `files` (path + full source) or run `dig review <paths>` locally, and check `reviewed.lines` matches the file. Fix findings by their file and line.
- Size by region; match controls within a row. Ordinary forms: ControlSizeProvider size="lg" mobileSize="xl"; dense toolbars: default. Nest providers, not height overrides. FormActions adapts widths/order: secondary then primary in DOM, no fullWidth/flex overrides.
- A control is sized against the text and controls in the same row: inside a list row (16px title, 14px price) or a cart line use 40px (ControlSizeProvider size="lg" around the list, or AddToCart size="lg"); 48px xl is for page-level forms, card footers on a product page and sticky bottom bars. A quantity stepper never grows wider than the button it replaces (AddToCart keeps both in one grid cell), and the title beside it stays on one line at 375px. Secondary controls (sort, filter, date range, category and view segmented ToggleGroups in a header or toolbar) are one step below the primary action and one more step down on phones: <ControlSizeProvider size="lg" mobileSize="default" asChild> around the ToggleGroup (40px desktop, 36px under 640px) inside an xl page; a segmented control inside a form next to fields keeps the field height. Active filters and tags are Chip (32px) with ChipCloseButton, never outline Buttons, with a small ghost «پاک کردنِ همه». _(list, mobile, detail pages)_
- Single-choice selectors (topic, category, sort, plan period, gender) are always ToggleGroup variant="segmented" (tabs), wrapped in overflow-x-auto on mobile; never outline toggle rows or chips for this. Exception: a product colour is always a row of colour circles (ColorSwatchPicker radius="full" indicator="ring", size lg on mobile) with the chosen colour name in the label, never text tabs.
- Choices that need a description (shipping, payment, time slot, branch) are RadioGroup items inside bordered cards with a checked border and subtle background; disabled options get bg-muted and a reason.
- Status is never color alone: pair it with an icon or text (Badge, Alert).

## Do's and Don'ts

### Do

- On mobile, secondary choices (filters, sort, actions on an item, pickers) open a bottom Drawer, not a centered Dialog or dropdown; the primary action of a screen (add to cart, pay, continue, send) is a full-width button fixed to the bottom above the safe area (pb-[env(safe-area-inset-bottom)]), never lost at the end of the scroll. _(mobile pages)_
- Do not float navigation buttons (back, close) over a swipeable image gallery; a chevron on a photo reads as next or previous image. Put back, share and like in the AppBar above the gallery and keep only the slide indicator on the photo. _(mobile, detail pages)_
- Every add-to-cart button is AddToCart: after the first tap it becomes a + / count / − stepper in place (trash at 1), same height and width, so the user sees and changes the quantity without opening the cart. Product detail pages drop the separate quantity field; a toast alone is not enough feedback. _(list, detail, mobile pages)_
- Anything an assistant does for more than a second is visible: Thinking while it reasons, ToolChips (status running/done/error) for every tool call, TaskRows for multi-step work with the current step marked. Raw logs go behind a chip's detail, never inline. _(chat pages)_
- Answers stream with StreamingText and the PromptInput send button turns into stop until the answer ends; the input stays editable meanwhile. Each answer offers copy, retry and feedback. _(chat pages)_
- When an answer is built from the user's files or data, show its sources with ContextCards (file name, type, snippet, total count) next to the answer. _(chat pages)_
- Before an irreversible or costly action (payment, delete, send, data change) the agent asks with ApprovalCard using verb-specific options, and data changes show a DiffTable of before and after first; never one approval for several different actions. _(chat pages)_
- Suggestions use RecommendationCard: one main suggestion, a short reason and one alternative; dismissing is always possible and never blocks the flow. _(chat pages)_
- Persian headings never use leading-tight or leading-none: Persian letters have tall ascenders, dots and descenders, so two-line headings at 1.25 line-height touch. Use leading-snug (1.375) or more for any heading that can wrap; leading-none only for single-line numerals.
- Price periods are words: «ماهانه» or «سالانه» (not «/ ماه»); Persian digits; signed amounts (+/−) go inside <bdi dir="ltr">. _(marketing, dashboard, list, detail pages)_
- Mix avatar types in any list of people: mostly portrait photos (<Avatar src alt icon={<AvatarGenderIcon />} />, icon as fallback), some AvatarGenderIcon, and only a few initials (name=). Never make every avatar initials.
- Show numbers with Persian digits (toFaDigits/formatNumber/formatCurrency), dates in Jalali (formatJalali), and wrap emails, URLs and phone numbers in <bdi dir="ltr">.
- Write warm, short Persian copy (errors, empty states, success); avoid formal or robotic sentences, emoji and the em-dash.
- Use fictional brands, people and companies in testimonials and examples; never attribute quotes to real companies.
- Do not put decorative icons inside form fields (e.g. a person icon in a name field). Icons in fields only when they carry meaning (search, password toggle). _(form, auth, support, checkout pages)_
- Heroes, covers, product and summary cards use real photos from the stock-images registry lib (stockImages.<name>.src with its Persian alt; light, no faces, WebP). Install it with the block; never hot-link random photos or leave grey placeholders on marketing and content pages. _(marketing, content, checkout, detail pages)_
- Files show a real file-type icon (FileTypeIcon from file-upload: PDF red, spreadsheet green, doc blue, archive amber) with name and size.
- Primary actions stay disabled until the action is possible (nothing selected, empty reply, upload in progress) and the label says why when useful (e.g. «منتظر پایان بارگذاری…»).
- Show results where the user is looking: success state replaces the form in place, errors sit under the field, toasts only for background confirmations.
- Every list or search has an EmptyState with a friendly reason and one way forward.
- Use motion only to explain change: count-up for key stats (CountUp), marquee for logo rows, Reveal for marketing sections and staggered card rows (delay index*100), small hover lifts on cards; never animate forms, tables or dashboards; always respect prefers-reduced-motion. _(marketing, dashboard pages)_
- Every status is said in words, not only colour: over budget shows «۴۲۰ هزار بیشتر از بودجه» plus Progress color="destructive"; delay, unread, error and success each carry text or an icon. Colour Progress with its color prop (or --progress), never by overriding --primary. Money: green only for incoming, outgoing stays the normal text colour (never red), and the sign sits in <bdi dir="ltr">.
- Search and filters always show the result count, keep active filters visible (segmented or removable chips) and every empty result offers a one-click way back («پاک کردنِ فیلترها»), never a dead end.
- A reversible, low-risk action (approve, archive, mark done, remove from list) runs on one click with no confirm dialog: update the row at once, then toast.success(title, { description: item name, action: { label: "بازگردانی", onClick: restore } }) where restore puts the exact previous item back and toasts the restored state. Keep the Undo toast long enough to reach (do not set a short duration). While the request runs show the busy label on that button and disable the paired actions; if it fails, change nothing, show an inline Alert role="alert" (and a toast.error) and let the user retry. Irreversible or costly actions (delete, pay, send) use AlertDialog instead. _(list, detail, dashboard pages)_
- Rejecting, declining or cancelling something someone else submitted needs a reason. Show the form where the button was (inside the same Sheet or panel): TextField with a TextFieldTextarea, required, maxLength with a live counter in TextFieldDescription, minimum length (about 10 characters) checked on trim, one Persian TextFieldError that names the fix, validated on submit and blur (noValidate on the form). Opening the form focuses the textarea; an invalid submit focuses it again; Cancel closes the form and returns focus to the Reject button; after a successful submit move focus to the result (status Alert, tabIndex -1) so it is never lost. Disable the fields while saving, and show the reason to the submitter afterwards. _(list, detail pages)_
- A data list or review table is assembled from Dig parts, never hand-built: StatStrip (summary) above, FilterBar (search, segmented status, Select, removable chips, result count, clear) then DataState (loading skeleton, error with retry, empty, filtered-empty with clear) wrapping the Table, TablePager as the footer, a detail Sheet on row click, and DecisionBar inside the Sheet for approve/reject (use toastUndo afterwards, see action-with-undo and reject-needs-reason), DescriptionList for the facts and Timeline for the history in that Sheet. Reset the page to 1 whenever a filter changes. _(dashboard, list pages)_
- Before calling a page done, pass the three Dig personas (PERSONAS.md). Arman (senior product designer): one primary action per view, Fitts (44px touch targets), Hick (few choices, staged long forms), progressive disclosure, recognition over recall, smart defaults (Jalali today, Iran), instant feedback and visible system state, undo for reversible actions and confirm dialogs only for destructive ones with a verb button («حذفِ حساب» not «بله»), every state designed (empty with next action, loading skeleton, error, very long text), verb-led Persian microcopy, permanent labels, WCAG 2.2 AA (4.5:1 text, 3:1 UI, focus visible, keyboard, drag alternative, live regions). Negar (product lead): works on a real 30-field form and a long table, nothing half-finished or «به‌زودی». Kaveh (frontend lead): code copies and runs, no console warnings, semantic landmarks and one h1. _(form, checkout, dashboard, mobile, marketing, content, detail pages)_
- Use section for a distinct topic with a heading and aria-labelledby. A single control needs a label, not a redundant section heading. Icon-only buttons need Persian aria-labels; decorative visuals are aria-hidden.

### Don't

- Don't use opacity or `/alpha` colors to show disabled, inactive or unchecked states.
- Don't use pill buttons (`rounded-full`), `rounded-2xl` or `rounded-3xl`.
- Don't mix control heights on one page or pass `size` to individual buttons.
- Don't put decorative icons inside form fields.
- Don't show Latin digits, Gregorian dates or emoji in Persian UI copy.
- Don't write raw hex, rgb or px values in components, or paste the brand color anywhere outside brand.css.
- Don't center long text or headers inside app pages; align to the start (right in RTL).
